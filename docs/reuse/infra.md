## 1. Bootstrap (`plugin/src/main/java/kr/zombierun/ZombieRun.java`)

`public final class ZombieRun extends JavaPlugin implements Listener`, with fields `CityGen gen`, `PackServer pack` and `Game game`.

**plugin.yml**
- `name: ZombieRun`, `main: kr.zombierun.ZombieRun`, `api-version: '26.3'`.
- `load: STARTUP` is required. The plugin must be enabled before the main world loads, so that `getDefaultWorldGenerator` is asked for the generator.
- Commands are declared in plugin.yml, not Brigadier: `zr` (alias `좀비`, permission `zombierun.op`, default op). They are handled by the classic `onCommand(CommandSender, Command, String label, String[] a)` override. There is no tab completion.

**Order of startup**
1. `getDefaultWorldGenerator(String worldName, String id)` returns `gen`. It ignores both arguments. Paper calls it because `bukkit.yml` has `worlds.zr_city.generator: ZombieRun` (the plugin name).
2. `onEnable()`:
   1. `saveDefaultConfig()`
   2. `Props.load(getResource("props.json"), getLogger())`. props.json is copied into the jar root by the build.
   3. `pack = new PackServer(this); pack.start()`, which starts the HTTP pack server.
   4. `registerEvents(this, this)`
   5. `getScheduler().runTask(this, this::setup)`. This defers setup by one tick: with STARTUP the world does not exist yet inside onEnable.
3. `setup()`:
   1. `getServer().getWorld(Layout.WORLD)`. If it is null, it logs severe and returns.
   2. `setDifficulty(EASY)`.
   3. Game rules use the 26.3 `org.bukkit.GameRules` constants, which are renamed in 26.3: `ADVANCE_TIME=false`, `ADVANCE_WEATHER=false`, `SPAWN_MOBS=false`, `FALL_DAMAGE=false`, `KEEP_INVENTORY=true`, `SHOW_ADVANCEMENT_MESSAGES=false`, `LOCATOR_BAR=false`, `RANDOM_TICK_SPEED=0`, `PVP=true`, `IMMEDIATE_RESPAWN=true`.
   4. `setTime(13000)` (dusk), `setStorm(false)`, `setSpawnLocation(Layout.lobby(w))`.
   5. World border centered on `(Layout.W/2, Layout.D/2)` with size 700.
   6. `game = new Game(this, w)`, then config values are copied into public fields (`grabSeconds`, `riderSeconds`, `autoStart`, `minPlayers`, `prepSeconds`, `shutterSeconds`).
   7. Registers `game`, `game.guns` and `game.zombies` as listeners.
   8. `runTaskTimer(this, game::tick, 1, 1)`. This is the only main loop: every tick, synchronous.
   9. For online players (the reload case): `game.glow.inject(p); game.toLobby(p)`.
4. `onDisable()`: `game.stop()`, `glow.uninject` for every player, `pack.stop()`.

## 2. State machine and per-player state (`game/Game.java`)

`enum State { LOBBY, PREP, RUN, FINALE, END }`. `tick()` is called every server tick:
- `tick++`, then a switch on state, then `hud.tick()` always.
- **LOBBY** runs `lobbyTick()`. If `autoStart` is on and at least `minPlayers` players are in game, it counts down `lobbySeconds(30)*20` ticks, shows it with `hud.phase(...)` (boss bar), then calls `start(0)`. If the count drops below the minimum, the countdown resets.
- **PREP** shows a countdown of `prepSeconds*20` and runs `guns.tick()`. At 0 it calls `beginRun()`, which opens the door, respawns the zombies, spawns the bots, plays a sound and sets `state=RUN`.
- **RUN/FINALE** runs `runTick()`:
  - `director.tick(alive(), zombies.entities())`, logged as `[감독] <event>`
  - `zombies.tick()`, `guns.tick()`, `grenades.tick()`, `loot.tick()`, `fx.tick()`
  - processes the `turning` map (infected players become zombies after 30 ticks)
  - shutter and exit geometry checks against `Layout.SUB_*`/`SHUT_*`, then the phase bar
- **END**: after 200 ticks, `reset()`.

`start(int bots, List<String> forced)`:
1. Collects in-game players, then `round++`.
2. Survivors are the players who have gone longest without being one (`lastSurvivorRound`). `forced` names override this, which is how tests pick roles.
3. `Route.random(rnd).build(world)`, `director.reset(...)`, `stats.reset(tick)`, `prepare` and `equip` each player, teleport, then `state=PREP; stateAt=tick`.

`end(boolean)`:
- Sets END and calls `guns.settle()`.
- Builds result lines from `Stats.top(...)`, sends them as chat and the big title, and logs `[판] 끝 ...`.

`stop()` calls `reset()`, which clears every subsystem (`zombies.clearAll`, `guns.clearAll`, `loot.clear`, `grenades.clear`, `fx.clear`, `hud.clear`, `glow.clear`), the route, and the blocks it placed, then sends everyone to the lobby.

**Clocks.**
- `Game.tick` (`now()`) always advances. `stateTicks()` is `tick - stateAt`.
- `Director.tick` only advances during RUN. The code comment says never to mix the two ("판 틱 g.now() 와 섞지 말 것").

**Per-player state** is spread across UUID-keyed collections in each subsystem:
- `Game`: `LinkedHashSet<UUID> survivors`, `List<UUID> roster`, `Map<UUID,Long> turning`, `Map<UUID,Integer> lastSurvivorRound`
- `Guns`: `arms(p)` gives `Arms`
- `Zombies`: `get(e)` gives `Zed`
- `Hud`: `Map<UUID,HudScreen> screens`

`onQuit` must call every `forget(id)`. For Gave, use a single `Map<UUID, PlayerState>` (currency, augments, stats, gun) and give each subsystem a `forget(UUID)`.

**Generic listeners worth copying**
- `onDamage` (LOW priority) cancels all damage to `Player`, `Mannequin` and zombies, so the damage model is fully custom. For Gave, fake mobs are `item_display`, so damage to players will be applied in code.
- `onFood` cancels and keeps food at 20.
- Inventory click and drag, entity interact, block break and place are cancelled for in-game players.
- `onCombust` and `onSpawn` (cancels NATURAL and REINFORCEMENTS).
- `onRespawn` sends players to the lobby.
- `onJoin`: `glow.inject`; in LOBBY or END, `toLobby`; otherwise the player joins as a zombie. For Gave this becomes spectator-until-next-wave or join the wave.

**Zombie-specific parts to drop or replace:** `Route`, the shutter/FINALE logic, `infect`/`turning`/`revive`, `GlowNet` (survivor glow seen only by zombies, a Netty handler `zombierun_glow`), the teams `zr_z`/`zr_s`, `Zed`, and `cfgGrabSeconds`.

**`status()` format:** `"[단계상태] state=<STATE> tick=.. survivors=.. zombies=.. ..."`. The test `until` step string-matches this, so keep `state=` and add Gave keys such as `wave=` and `mobs=`. The `[판] ...` log lines are the post-game analysis feed, so keep a stable prefix.

## 3. World generator wiring (`world/CityGen.java`)

- `CityGen extends ChunkGenerator`. `generateNoise(WorldInfo, Random, cx, cz, ChunkData)` loops over columns and calls `column(d, lx, lz, worldX, worldZ)`.
- Each column is a pure function of (x, z) using `Layout.hash`/`seed`, so the result does not depend on chunk order. Copy this pattern.
- Ground at `Layout.G = 64` with stone from G-4 to G.
- `getDefaultPopulators` returns `List.of(new Decor.Populator())`, which places persistent `item_display` props at generation time.
- Every `shouldGenerateNoise/Surface/Caves/Decorations/Mobs/Structures()` returns false.
- `getFixedSpawnLocation` returns `Layout.lobby(world)`.
- `getDefaultBiomeProvider` returns a single `Biome.PLAINS`.
- **Gotcha:** `Decor` reads prop models from the pack zip during chunk generation. It looks at `zombierun.packDir`, otherwise `dataFolder/../../../build/ZombieRun-pack.zip`. `CityGen` calls `Decor.lampsReady()`/`Decor.alleyProps()`. If the pack is missing when the world is first created, the fallback blocks are baked into the world permanently. Build the pack first, then generate the world (`--fresh-world`).
- **Making a fresh world:**
  1. Stop the server and delete `runtime/<level-name>` (for slot tests, `--fresh-world` deletes `runtime-9/zr_city`).
  2. Start the server again.
  - The base `runtime/` deliberately contains no world folder. The names must match in four places: `server.properties level-name`, the `bukkit.yml worlds.<name>.generator` key, `Layout.WORLD`, and the `WORLD` constant in ingame.py.
  - `allow-nether=false` and `allow-end: false`, so only the overworld is created.

## 4. Test tooling

### build_plugin.sh
- Runs an inline Python heredoc. javac is called with `--release 25 -encoding UTF-8 -proc:none`. The classpath is `runtime/libraries/**/*.jar` plus `runtime/versions/**/*.jar` (`paper-26.3.jar`).
- Output goes to a fresh temp dir `build/plugin/compile-*`. It copies `plugin/src/main/resources` and `tools/props.json` in, then writes `build/ZombieRun.jar`.
- It probes `127.0.0.1:26000`:
  - If the port is up, it does not copy into `runtime/plugins`. Replacing a jar under a running server causes `NoClassDefFoundError`.
  - If it is down, it copies the jar to `runtime/plugins/ZombieRun.jar`.

### compile_wip.py (isolated compile for parallel agents)
- `--name <n>`: copies `plugin/src/main` to a temp dir, overlays `build/wip/<n>/plugin/src/main/**`, and compiles to `build/<n>/ZombieRun.jar`. The jar is written atomically through `.tmp.jar` and `os.replace`.
- `--promote`: after a successful compile, moves the wip files into the real tree (tmp copy plus `os.replace`) and deletes them from wip.
- `--real`: compiles the real tree only, to `build/real/ZombieRun.jar`.
- It never touches `runtime/plugins`. The exit code is 0 or 1.

### test_server.sh (`start | stop | rcon <cmd>`)
- Slots come from `ZR_SLOT=N`. `RUNTIME` is `runtime` for slot 0, otherwise `runtime-N`. Ports are `26000+10N` (game) and `26001+10N` (RCON), the pack port is `8250+N`, and `PASSWORD='zombierun-dev'`.
- The header comment says "25820+10N, 8190+N". That comment is stale; the code is right.
- `prepare_slot()`:
  - It copies `runtime` to `runtime-N` only if the slot folder does not exist yet, ignoring `logs`, `session.lock`, `stats.json` and `matches`.
  - Later edits to `runtime/*.yml` do not reach an existing slot. Edit or delete the slot folder.
  - It forces these `server.properties` keys: server-port, query.port, enable-rcon, rcon.port, rcon.password, `online-mode=false`, white-list and enforce-whitelist false, and the motd.
- `start`:
  - Refuses if a tracked process is alive, then checks the ports on both IPv4 and IPv6 with `SO_EXCLUSIVEADDRUSE`.
  - Installs the jar: `ZR_JAR` if set (always copied), else `build/ZombieRun.jar` if it is newer than the installed one.
  - Launches `java -Xms1G -Xmx${ZR_XMX:-3G} -Dfile.encoding=UTF-8 ... -Dzombierun.debugShots=true -Dzombierun.packPort=<8250+N> [-Dzombierun.packDir=$ZR_PACK_DIR] [-Dzombierun.packRepo=$ZR_PACK_REPO] -jar paper.jar --nogui --noconsole`. `debugShots` is never read by the Java code (dead). Output goes to a file only (`build/server[-N].log`), with `CREATE_NO_WINDOW|CREATE_NEW_PROCESS_GROUP` and stdin set to DEVNULL. Never pipe it: the Windows pipe hang.
  - Writes `build/server-process[-N].json` = `{pid, birth (process creation FILETIME), runtime}`, so stop never kills a process whose PID was reused.
  - Ready means `Done (` appears in the log and the RCON port accepts a connection. The timeout is `ZR_START_TIMEOUT` (default 420 s).
- `stop`: sends RCON `stop`, waits 60 s, then calls TerminateProcess only if the birth time matches, then re-checks that the ports are free.
- Its RCON client sends an empty marker packet after the first reply, to collect multi-packet responses.

### ingame.py (one in-game test at a time)
Arguments:
- `--name` (required)
- `--scenario` (repeatable, required)
- `--second-user`
- `--second-scenario` (default `tools/scenarios/idle.json`)
- `--backend` (default `opengl`)
- `--fresh-world`
- `--keep-pack`

Constants: `SLOT=9`, `PORTS=(26090,26091,8259)`, `WORLD=runtime-9/zr_city`, `CLIENT_DIR="zombierun-client-9"`.

Flow:
1. Requires `build/<name>/ZombieRun.jar`.
2. **Lock**: an OS lock (`msvcrt.locking LK_NBLCK`) on `build/locks/ingame.lock`. The owner is written to `build/locks/ingame.owner.json` as `{pid,name,since}`. It waits up to 90 minutes and prints every 60 s. It is released automatically if the holder dies.
3. `clear_slot`: if the state file exists or a port is busy, it runs `test_server.sh stop`. If the slot is still busy, it exits without touching the world.
4. Creates a `ClientJob`: a Windows Job Object with `KILL_ON_JOB_CLOSE`, named `zombierun-ingame-<pid>-<ns>`. Client wrappers are started through `job.popen`, which passes `ZR_JOB` in the environment. `client_run.wait_for_job()` waits until it is inside the job before starting Java, so Java dies with ingame.py. `kill_slot_clients()` kills leftover quickPlay Java processes whose command line contains `CLIENT_DIR`.
5. Pack: runs `tools/build_pack.py` with `ZR_PACK_OUT=build/<name>/ZombieRun-pack.zip`, unless `--keep-pack` is given and the zip exists.
6. `--fresh-world`: checks the slot again, `rmtree(WORLD)`, and aborts if the folder survives.
7. `test_server.sh start` with `ZR_JAR=build/<name>/ZombieRun.jar` and `ZR_PACK_DIR=build/<name>`. The common env is `ZR_SLOT=9 ZR_XMX=2G ZR_CLIENT_XMX=2G ZR_TAG=<name> ZR_RCON_MAX=600`.
8. `wait_clients(need)`: a **PC-wide** cap of 2 Java processes with `--quickPlayMultiplayer` on the command line, across every project. Keep this logic identical in Gave. It waits up to 30 minutes.
9. Optional second client: `ZR_USER=<second>`. It waits up to 240 s for `팩 상태 <user> SUCCESSFULLY_LOADED` in `server-9.log`, then sleeps 4 s.
10. Each scenario runs `client_run.py <sc>`. The log is `build/<name>/client_<stem>.log`, and the last 60 lines are printed.
11. `finally`: kills the second client's process tree (`taskkill /T /F`), closes the job, kills leftover slot clients, runs `test_server.sh stop`, copies `build/server-9.log` to `build/<name>/server_<n>.log`, and releases the lock.

Screenshots go to `build/shots/<scenario-stem>_<ZR_TAG>/<shot>.png`, which is `_<name>` when run under ingame. That folder also gets `client_latest.log`, and on failure `client_fail_<k>*.log`/`stdout`/`hs_err`.

`client_run.rcon` is a single-read client: auth with the password, then read one response packet. Keep replies short. `tools/rcon_cmd.py "cmd" "wait 3" ...` reuses it.

**Faking input.** The 26.3 client is SDL3. Keys are dropped without keyboard focus, and mouse clicks arrive but land at the real OS cursor position (winpost docstring). So movement, aim and firing are done server-side. `ZombieRun.test(String[] a)` handles `/zr 시험 <action> <name> [args...]`:
- `a.length < 3` returns a usage string.
- The special global case is `봇정지 on|off` (`Mob.setAware`).
- `p = getPlayerExact(a[2])`. If p is null, it calls `moduleTest(null, a)`. Global hooks pass a dummy third word, for example `zr 시험 출발 x`.
- Numeric args come from `a[3..]`, parsed to doubles (NaN when not a number).
- Built-in actions:
  - `쏘기 n` calls `guns.testFire`
  - `재장전`, `수류탄`, `수류탄주기`, `줍기`, `총 <KIND>`
  - `보기 x y z`: teleport with `setDirection` toward the point. The server sets yaw and pitch, and that moves the client camera.
  - `보기좀비`, `보기사람 <name>`, `옆으로 <name> [dist]`
  - `이동 x y z`, `길 <dist>`, `감염`, `죽이기`, `특수 <TYPE>`, `능력`
- Anything else goes to `moduleTest`: `zombies.test`, then `guns.test` (which chains `loot`, `grenades`, `fx.shots`), then `hud.test`, then `MapTest.test(game,p,a)`. The convention is `public String test(Player p, String[] a)` returning null when the action is not handled. `p` may be null for global hooks.
- `Zombies.test` holds the global hooks (`판끝막기 on`, `출발`, `감독`, ...).
- For Gave, keep the dispatcher and the `보기`/`이동`/`쏘기`/`총`/`재장전` hooks, and add `웨이브 n`, `돈 <name> n`, `상점 <name> <slot>`, `몹소환 n`, `몹정지`.

Example scenario patterns are in `tools/scenarios/smoke.json`, `shoot.json`, `infra.json` and `zed_main.json`. A typical shape is `["cmd","zr 시작 6"]`, `["until","state=RUN",30]`, `["cmd","zr 시험 보기좀비 {USER}"]`, `["shot","aim"]`. `idle.json` is `[["wait",110]]`, used to keep a second client online.

`spigot.yml` and the `config/` files look like stock Paper output: same write time as the rest, nothing hand-tuned found.

**Do not copy:**
- `logs/`
- any world folder (the base runtime has none; `runtime-9/zr_city` has 17 MB)
- `plugins/ZombieRun.jar` and `plugins/ZombieRun/` (config, `map_undo.txt`)
- `plugins/bStats`, `plugins/spark` (regenerated by Paper's bundled spark)
- `usercache.json`, `banned-*.json`, `whitelist.json` (regenerated)
- `crash-reports/`, `session.lock`
- any `runtime-N/` folder. Slot folders are created by `test_server.sh` on first use, and each one duplicates about 217 MB; the user's memory notes C: is low on space.

**First run:**
1. Build the pack.
2. Run `compile_wip.py --real` (or `build_plugin.sh`).
3. Run `ingame.py --name real --scenario ... --fresh-world`, so the world is generated after the pack exists.
